- `libs/typewriter-runtime/src/lib/typewriter-serializer.spec.ts` - Added 3 tests for date backend serialization (default, custom, unsupported tolerant)

**Design decisions:**
- `DateSchemaKind` has 8 semantic kinds: `instant`, `plain-date`, `plain-time`, `plain-date-time`, `zoned-date-time`, `duration`, `plain-year-month`, `plain-month-day`
- `DateBackend` has a `name` and partial `codecs` map - backends only advertise kinds they can honestly represent
- Missing codecs: strict mode throws `Date backend "X" does not support Y`, tolerant mode preserves original value
- Temporal is the built-in default (already a peer dep of `typewriter-runtime`), so existing code works without changes
- `defineDateBackend()` is an identity helper; most backends use `satisfies DateBackend` with type-only imports instead

**Recommended new annotation:**
```csharp
public enum FrontendDateLibrary
{
    Auto,     // Use template/generator default
    Temporal, // @js-temporal/polyfill
    Moment,   // moment
    Luxon,    // luxon
    DateFns,  // date-fns (native Date)
    DayJs,    // dayjs
    JsJoda,   // @js-joda/core
}

[AttributeUsage(
    AttributeTargets.Assembly | AttributeTargets.Property |
    AttributeTargets.Field | AttributeTargets.Parameter)]
public sealed class FrontendDateLibraryAttribute(FrontendDateLibrary library) : Attribute
{
    public FrontendDateLibrary Library { get; } = library;
}
```

**Precedence:** `FrontendNoTransform` > member `FrontendDateLibrary` > assembly `FrontendDateLibrary` > template default.

**Key issue:** Roslyn's `FormatTypedConstant` uses `TypedConstant.Value.ToString()` which surfaces enum members as numeric values, not names. The `.tst` template would need to map numeric values back to library names, or Typewriter must be extended to surface enum member names. See `CSharpProjectMetadataProvider.cs:1362-1382` and `TemplateAttributeValueFormatter.cs`.

**Assembly-level attributes are NOT currently surfaced** to `.tst` templates. `ProjectMetadata` has no assembly attributes collection. Either:
- Extend Typewriter to expose assembly attributes (requires changes to `CSharpProjectMetadataProvider.cs`, `CodeModel\File.cs`, `TemplateCodeModelAdapterFactory.cs`, `TemplateRenderer.cs`)
- Or use existing template configuration (`Settings.UseDateType()`, `typewriter.schema.json` `output.dateType`) for global default and restrict `FrontendDateLibrary` to member-level overrides only

## Architecture Summary

```
User selects date library via:
  1. Template configuration (Settings.UseDateType / typewriter.schema.json)
  2. [FrontendDateLibrary] attribute on property/assembly (pending)
  3. Runtime options: { dateBackend: momentDateBackend }

     ┌─────────────────────────────────────────────────────────┐
     │ typewriter-runtime                                      │
     │   transformJson(json, schema, registry, { dateBackend })│
     │   serializeJson(value, schema, registry, { dateBackend })│
     │   default: temporalDateBackend (built-in)               │
     └──────────────────────┬──────────────────────────────────┘
                            │ dateBackend option
     ┌──────────────────────┴──────────────────────────────────┐
     │ DateBackend codecs per kind                             │
     │  temporal: all 8 kinds    luxon: all 8 kinds            │
     │  js-joda: all 8 kinds     moment: 4 kinds               │
     │  date-fns: 4 kinds        dayjs: 4 kinds                │
     └─────────────────────────────────────────────────────────┘

HTTP adapters forward dateBackend through options:
  Angular: withTypewriterResponseSchema(schema, { transformOptions: { dateBackend } })
  Axios:   { responseTransformOptions: { dateBackend } }
  Fetch:   fetchJson(url, schema, init, { transformOptions: { dateBackend } })
  RTK:     createTypewriterTransformResponse(hydrate, { dateBackend })
```
